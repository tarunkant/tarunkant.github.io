Zero-Day No More: CloudFront Misconfiguration Discovery and Resolution

SpyClub
2025-07-30
blog
0day, AWS, Amazon, Bug, Cloudfront, Subdomain Takeover

Hey, I am SpyD3r (@TarunkantG) and in this blog, I will be discussing an important mis-configiration pattern that I discovered, and reported to AWS, during routine experimentation that infrastructure teams should be aware of when setting up their CDN services. This configuration pattern, if left unaddressed, could have allowed attackers to take over any domain configured via CloudFront with an S3 static website origin, under certain specific setup conditions, and could have served serve malicious content under a trusted name and this all without needing access to the original infrastructure. Read on for a deep dive into how this works and how this could have led to real world abuse before it was reported through AWS’s Vulnerability Disclosure Program.

👋 Introduction

In the world of cloud infrastructure, AWS CloudFront is one of the most trusted global CDNs used to serve web assets fast and securely. It’s the backbone of performance for countless high-traffic sites, from static blogs to enterprise-grade apps. However, while testing various edge-case behaviors, I stumbled upon a subtle but critical misconfiguration that could allow complete domain takeovers for sites hosted via CloudFront with an S3 static website origin.

This isn’t just about misconfigured DNS or a forgotten bucket, this is about how a seemingly safe AWS-managed origin request policy can be exploited to serve attacker-controlled content under trusted domains.

This blog is a detailed walkthrough of how the bug worked, how I discovered it, and how real-world configurations were potentially vulnerable to this kind of attack.

It is important to note that there has been no observed or reported abuse of AWS. After I informed AWS of my findings, they made updates which mitigated the issue. It can no longer be exploited, and AWS customers do not need to take further action.

⚙️ Background: How S3 and CloudFront Usually Work Together

Many organizations configure their domains to point to a CloudFront distribution, which in turn uses an Amazon S3 static website as its origin. A common use case for this is to enable HTTPS on root domains, something DNS limitations (like the inability to use CNAMEs at the apex level) would otherwise complicate.

A typical setup may look like:

  • Domain spyclub.tech → CloudFront Distribution
  • CloudFront → Origin: Either http://spystorageclub.s3-website-us-east-1.amazonaws.com or http://spyclub.tech.s3-website-us-east-1.amazonaws.com
  • Behavior → Origin request policy: Managed-AllViewerAndCloudFrontHeaders-2022-06

At a glance, this setup seems secure and functional. But underneath the surface, it carries a potential risk tied to how CloudFront constructs requests to S3 static websites.

🛑 The Vulnerability: Where It All Goes Wrong

When you configure CloudFront to use an S3 static website as an origin along with vulnerable origin request policies, you introduce an implicit trust based on the Host header.

Here’s what’s really happening:

  • S3 static website hosting relies heavily on the Host header to resolve buckets.
  • The Managed-AllViewerAndCloudFrontHeaders-2022-06 policy forwards the full Host header from the incoming request to the origin.
  • If CloudFront receives a request for spyclub.tech, it forwards that as-is even if the origin is set otherwise.
  • If no bucket named spyclub.tech exists, S3 returns NoSuchBucket.
  • But if someone creates a public S3 website bucket named spyclub.tech, CloudFront happily serves that content instead.

That’s the entire crux: Generally, CloudFront retrieves content by first accessing the configured origin endpoint. But as part of this process, CloudFront includes additional headers based on the origin request policy settings. The S3 endpoint then fetches the matching content from the appropriate S3 bucket using the host header information, which in this case could be different from the configured origin endpoint.

And this, my friends, is where the house of cards begins to fall.

🔥 Real-World Scenarios and PoCs

I have outlined three distinct scenarios where this misconfiguration could have been abused, ranging from simple setups to advanced origin sharing tricks.

🚨 Scenario 1: Bucket Name NOT Matches Hostname — Classic Root Takeover

Let’s say spyclub.tech is a root domain pointing to CloudFront. The origin S3 bucket is named something else entirely in it’s CloudFront policy, say spystorageclub, i.e. CloudFront distribution of spyclub.tech points to S3 origin with spystorageclub.s3-website-us-east-1.amazonaws.com. Note that spystorageclub bucket in the picture but NOT spyclub.tech.

Visiting spyclub.tech works as expected, but adding any path like /test.html throws a NoSuchBucket error.

Why? Because the forwarded Host is spyclub.tech, and S3 has no bucket with that name.

🧪 Exploit Steps

  1. Attacker creates a public S3 static website bucket named spyclub.tech.
  2. Enables static website hosting and uploads index.html and other payloads.
  3. Visiting https://spyclub.tech/index.html now serves attacker-controlled content from an S3 bucket they own, under a domain they don’t.

🔁 Scenario 2: Multiple Domains, One Distribution — Cross-Origin Poisoning

Modern infrastructure often reuses the same CloudFront distribution across multiple domains to save cost and simplify routing logic.

Consider:

  • spy.club is a vanity redirect domain.
  • spyclub.tech is the main production domain and an S3 bucket exists with this hostname.
  • Both point to the same CloudFront distribution.
  • No bucket named spy.club exists.

🔓 Exploit Vector

  1. Attacker creates a public S3 bucket named spy.club.
  2. Uploads malicious HTML payload.
  3. Triggers it via spy.club/path/payload.html.
  4. CloudFront caches the attacker’s content.
  5. Since the cache is shared, this payload can now be served from spyclub.tech too!

What This Enables:

  • Cache poisoning across domains
  • Credential phishing hosted on spyclub.tech
  • Drive-by malware served from a legitimate domain

🕵️‍♂️ Scenario 3: Bucket Name Matches Hostname — CDN Hijacking

In this scenario, the S3 bucket name matches the domain name, but due to the Managed-AllViewerAndCloudFrontHeaders-2022-06 origin policy, even the CloudFront URL returns a “bucket does not exist“ error. If somehow, the CloudFront URL gets leaked, an attacker could have exploited this by creating an S3 bucket with the same name as the CloudFront URL.
Once the CloudFront bucket is created, they could upload malicious content and force it to be cached in the CloudFront distribution. Since this CloudFront distribution is linked to the main domain, the attacker could have ultimately served malicious content directly from the trusted main domain.

tl;dr

These distribution URLs behave the same way:

  • If no matching S3 static website exists, CloudFront returns no bucket exists error.
  • If an attacker claims a bucket matching the CloudFront subdomain, they can now host and cache arbitrary files.

Why does this matter?
Because cached files under the CloudFront distribution can later be served via trusted custom domains mapped to the same CloudFront distribution.

Who all were affected?

All the domains that were using a CloudFront distribution pointing to an S3 static website with the Managed-AllViewerAndCloudFrontHeaders-2022-06 origin policy were affected by this. The issue is exploitable in both cases: when caching is disabled (as in Scenario 1), where CloudFront forwards every request to the origin; and when caching is enabled (Scenarios 2 and 3), where the impact can be more severe due to how objects are cached and served. For the attack to succeed, the requested S3 bucket must not exist, and the bucket name must match the domain name or the CloudFront distribution name.

As of June 26, 2025, the Managed-AllViewerAndCloudFrontHeaders-2022-06 managed policy is no longer available for S3 origins with Amazon CloudFront Distributions. AWS proactively notified affected customers and recommended they update their CloudFront distribution to remove this policy. In addition, customers do not need to take any action.
